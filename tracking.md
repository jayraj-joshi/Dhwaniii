## How to resume in a new session

1. Read `planning.md` (decisions D1–D48 and §11 milestones), then this file, then `structure.md`.

4. At the end of every milestone: run its tests, record acceptance results here with dates and numbers, update `structure.md`.

## Implementation notes (things the plan left open)

- `parse_title`, pipe-only titles (no dash): read as `title | album | …` with the artist taken from the channel. Taking planning.md §9.2 literally would make segment 1 the artist, which is wrong for `Tum Hi Ho | Aashiqui 2 | HD`. Dash titles follow the plan exactly.
- `parse_title` returns `{title, artists, featured, album, year}`; `album` and `year` are `None` when unknown.

- Search SQL must not use a CTE for the query string: the planner then seq-scans (60 ms at 10k rows vs 2 ms with `$1` inline). After a bulk load run `ANALYZE` or timings will look 30x worse until autovacuum catches up.
- `/api/search` songs are scored in SQL (id + score), then hydrated with `get_tracks`, which returns Track objects in that order. `top` is `{kind: 'artist'|'song', item}`.
- Playlist summaries (`playlist_json`) currently live in `routes/search.py`; move them when M1.14 adds playlist routes.
- Native-script (Devanagari) queries work with the `simple` tsvector and pg_trgm on this Postgres image; the risk noted in §13 did not materialise in the fixture.

- **youtube.py decisions:** ytmusicapi is tried first with a 6 s timeout; yt-dlp `ytsearch10:` runs only if it fails or returns nothing. `remote=always` (the "More from YouTube" button) merges both lists, which is the case where §9.4's "duration within ±10 s of the top ytmusicapi entry" applies. Cache keys are `ys:songs:<nq>` and `ys:more:<nq>`; empty results are never cached.
- **RemoteTrack additions:** besides §7.1 fields it carries `channel` and `quality_score`, so `ensure_track` (M1.6) can store them on `sources` without re-ranking. They are optional on a TrackHint.
- **Ranking fix vs the literal §9.4 text:** "channel equals parsed artist" only counts artists named in the YouTube title (`title_artists`) or by ytmusicapi. `parse_title` falls back to the channel name when a title has no separator, which would make the signal true for every result.
- **Known limitation:** yt-dlp fallback titles that contain an extra ` - ` can be mis-split by `parse_title` (e.g. `Kesariya … - Film Version` shows title "Film Version"). Only visible in `remote=always` lists; the real metadata is fixed when the file is downloaded (M1.8) and by enrichment in M2.1.

- **ensure_track and provisional rows:** the track title/artists come from `parse_title(hint)`; with no artists in the hint it falls back to the title text and then the channel, then to `Unknown Artist`. Art for a provisional track 404s until the worker downloads it (the client uses `thumb_url` from the RemoteTrack meanwhile).

- **Stream details beyond the plan:** with no `Range` header from the client the proxy still asks upstream for `bytes=0-` but answers `200` without `Content-Range` (RFC 9110 forbids `206` for a non-range request). Upstream failures map to 502, "private/removed/unavailable" to 404. A cached `files` row whose file is missing on disk is treated as a miss.
- **config.py path rule:** `AUDIO_DIR` and `YTDLP_COOKIES_FILE` resolve relative to the repo root (`ROOT`), so `./audio` means the same folder whether the server starts from `server/` or from compose. Absolute paths (containers) are untouched.
- **Known limitation:** the first stream request after a server start costs about 5 s (later cold videos 1.5–2 s). Likely yt-dlp's first-run setup. If it matters, run one throwaway `_resolve` in the background at startup (tests would need it stubbed).
- **yt-dlp CLI note:** `--extractor-args youtube:player_client=…` variants returned instantly with no URL on this machine, so they are not a shortcut.
- D27 failed-job rule as built: a `low` request never revives a `failed` job; a `high` request (play, explicit cache) resets attempts and requeues it.

- **Worker decisions beyond the plan:** (1) `parse_title` returns a `stage`; a download only overwrites a provisional track's metadata when yt-dlp gave real music metadata (`fields`/`topic`), never for a rule-based title guess, so a clean ytmusicapi hint is not made worse. (2) `files.bytes` is read after tagging so `SUM(bytes)` matches disk. (3) `STORAGE_LIMIT_GB` is read as GiB (1024³ bytes). (4) The permanent-error test is one regex (`youtube.UNAVAILABLE_RE`) shared with the stream route; yt-dlp words it several ways ("This video is unavailable", "Video unavailable", "Private video") and "HTTP 503 Service Unavailable" must stay transient. (5) Progress events are throttled to 2 per second inside the yt-dlp hook. (6) A job that crashes mid-run stays `running` until arq retries it; there is no sweeper yet.
- **Download cost on this machine:** play-to-cached is about 11 s for a 4-minute track; loudnorm alone is about 5 s of that (spike), so it is the one place to optimise if the 5–20 s target gets tight on a Pi.

- **WebSocket notes for the client (M1.10+):** (1) Messages are dispatched by `type`; `state` is not guaranteed to be the very first message (a `devices` broadcast from a socket that just left can arrive before it). (2) Unknown profile is a handshake rejection (HTTP 403), not a close code, so the client should check `/api/me` or the stored profile before connecting. (3) `player_state` is relayed only from the active device; a device that starts playing becomes active and every device gets `active_device {device_id, resume:false}`: the client must pause when `device_id` is not its own. (4) The `transfer` message is ignored until M4.1. (5) `playback_state.state` holds the last `queue_update` merged with the active device's `position_ms`/`playing`.
- **Disconnect cleanup runs as a detached task.** Starlette's test client (and server shutdown) can cancel a handler; the `devices` broadcast and `last_seen` update must still happen. A socket closed because the same device reconnected raises `WebSocketDisconnected` in its old handler, which is caught.
- **Test harness tips:** run WebSocket tests under a hard timeout (`perl -e 'alarm 120; exec @ARGV' uv run ... pytest`; macOS has no `timeout`), because a missing message blocks `receive_json` forever. `-o faulthandler_timeout=N` shows where.

- **Cold-start fix (found in M1.10):** a fresh API process paid ~4.3 s on its first search (YouTube Music client setup) and ~5 s on its first stream (yt-dlp's first extraction). `youtube.warm_up()` now runs as a background task in the lifespan; first search after restart 0.61 s, first stream 1.97 s. Tests stub it out. The warm-up makes one real search and one real resolve at startup (offline is harmless).
- **How the browser acceptance was run:** no Chrome extension was connected, so a scratchpad script (`puppeteer-core` + `/Applications/Google Chrome.app`, headless, `--autoplay-policy=no-user-gesture-required`) drove `http://localhost:5173` against the host-run API/worker. The script is not in the repo. Real Chrome has the AAC codec, so m4a decodes. Not yet run on Safari, Firefox, Android or iOS (device matrix is for the end of Phase 1).
- **Still open from M1.9:** the "two tabs, starting playback in B pauses A" check needs the client logic from M1.13 (the server side is covered by tests).

- **Scope change 2026-10-12 (D48):** the user asked for the backend to be built first and the frontend separately later. planning.md now has D48, a "Track split" table at the top of §11, `-B`/`-F` milestone tags, a new `GET /api/tracks/{id}/candidates` endpoint (needed by M2.3-B), and a note that migration numbers follow the order they are written. `web/` stays as the M1.10 dev harness (Vite + React + Tailwind, `npm run dev`); do not extend it.

## Autoplay: three examples per batch (2026-10-12, at the user's request)

**What changed:** the first batch of a radio still uses the playing song alone. From the second batch on, the job picks **3 random songs of the previous batch** (`autoplay.sample`; all of them if the batch has fewer) and puts them in **one** Tavily query (`"<title> <artist>, <title> <artist>, <title> <artist> similar songs"`) and **one** model prompt that names all three and forbids returning any of them. The job remembers each published batch in Redis (`ap:batch:...`, 6 h) and only uses it when the client's list length equals the length that batch produced, so a client that dropped the batch, or a different radio, falls back to the playing song. A batch generated for a playlist/album/artist/liked context is recorded for the `radio:<seed>` the client starts from it. Titles are cached under the sorted example ids. ## Download to device (2026-10-13)

Added a way to save a track's audio as a real file in the OS downloads folder (file manager, not the PWA's IndexedDB offline cache from M4.2, which is still unbuilt). `GET /api/stream/{video_id}?download=1` serves the cached file with `Content-Disposition: attachment; filename="Artist - Title.m4a"` when it's already on disk, 409 otherwise. Tests in `server/tests/test_stream.py` (attachment header content, 409 on a miss).

**Bug found and fixed the same day:** the first version pointed a plain `<a download>` at the cross-origin API URL. A browser only honors `download` for a cross-origin link when the response already carries `Content-Disposition: attachment`; on any other response (the track not cached yet, a missing profile) it just navigates the tab to the error body instead, and Chrome's built-in JSON viewer for that error is itself an HTML document — which is the "HTML file" that showed up instead of an MP3. Reproduced with a headless-Chrome CDP driver hitting the real endpoint. Fixed by having `downloadToDevice()` (`web/src/lib/tracks.ts`) `fetch()` the file as a blob and save that via an object URL instead, so a failed request surfaces as a toast rather than a silent wrong download; the filename is read from the server's `Content-Disposition` header, which needed adding to the CORS `expose_headers` list (`server/app/main.py`) to be readable cross-origin. Re-verified the same way: downloaded file is the correct audio bytes named `Artist - Title.m4a`.
